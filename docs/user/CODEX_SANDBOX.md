# Codex 会话沙箱（Sandbox）

每个角色绑定独立解析当前项目策略、权限档案版本、角色路径范围和真实工作目录，不使用全局可写开关。创建、恢复先显式只读并禁止提权；每次模型输入前重新授权，再通过官方 `turn/start.sandboxPolicy` 设置只读或工作区可写。工作区可写只包含当前会话目录，关闭额外临时目录写入和命令网络访问；不使用 danger-full-access 或 externalSandbox。其他角色、项目和目录不因此获得写权限。

## 路径授权

- `*` 仍只匹配一层；旧规则含义不变。
- 新增末尾 `**`：`**` 授权项目内任意深度内容，`src/**` 授权 src 的后代内容。禁止中间位置的 `**`、父路径和绝对路径。
- `writePaths: []` 的角色使用只读沙箱。
- 非空 writePaths 必须完整覆盖该会话目录的递归子树；非空角色 scopePaths 也必须覆盖同一子树。例如会话在项目的 `workspaces/codex`，可用 `workspaces/codex/**`。即使档案授权整个项目，原生可写根也仅取该会话工作目录。
- 有限深度或单文件授权不能无扩大地映射到官方 workspaceWrite；此时明确拒绝，提示 `CODEX_SANDBOX_RECURSIVE_GRANT_REQUIRED`。不悄悄升级到完全可写。`enforced_paths` 仍未提供通用路径强隔离支持。

## 升级与使用

新建项目并明确选用 Alpha 三角色模板时使用递归授权。已有项目不自动修改权限；旧的 1—16 层星号规则不会自动变成递归规则。需要可写时，由用户通过已有 policy.configure 控制入口显式更新项目策略及角色所引用的权限档案版本；管理 Agent 不能自行扩大权限。只读与可写应使用不同角色、权限档案和原生会话，不能同时占用同一原生会话。

新授权在下个安全轮次生效；已运行中的命令不会被追溯撤销。目录不在项目内、junction/symlink 身份变化、策略版本冲突、暂停或结束绑定会拒绝新的输入。内核在真正写入 RPC 前再次核对授权，避免排队期间的撤权竞争。官方端不确认只读/禁止提权配置时不发送模型输入。

## 已测试及范围

Windows、本机官方 Codex CLI 0.166.0-alpha.5.1，模型 gpt-6-luna：两个真实会话同时只读/可写、关闭后同 ID 恢复，合计4轮输入通过；真实文件创建/追加及只读拒绝通过。官方 command/exec 测试确认授权根内写入成功、根外写入和只读写入被拒绝。首次探针把 app-server 启动在共同父目录，发现其隐含根会扩大命令写范围；生产适配器始终启动在本绑定目录，后续按此条件验证通过。

这是本次沙箱专项验证，不代表重跑完整协作流程，不是 Harness 版本白名单。只读沙箱限制文件写入，不声称限制所有文件读取；控制面/MCP 的独立动作权限继续由 ProjectOrch 检查。其他 Harness 不因本改动获得相同沙箱保证。
